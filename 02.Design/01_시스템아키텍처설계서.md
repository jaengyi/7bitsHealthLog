# 시스템 아키텍처 설계서

**개인용 운동기록 애플리케이션 (가칭) MyFit · v1.1**

> 관련 요구사항: `REQ-NFR-007`(아키텍처), `REQ-NFR-003`(오프라인), `REQ-DAT-001`(로컬 우선), `REQ-DAT-002`(동기화), `REQ-NFR-010`(백엔드 운영)

---

## 1. 설계 원칙

| # | 원칙 | 설명 | 근거 요구사항 |
|---|---|---|---|
| P1 | **Local-First (로컬 우선)** | 단말 Room DB가 단일 진실 공급원(SSoT). 서버는 백업·다기기 동기화 채널일 뿐이며, 서버 장애가 앱 사용을 막지 않는다. | REQ-DAT-001, REQ-NFR-003 |
| P2 | **Offline-Complete** | 기록·조회·분석 전 기능이 네트워크 없이 동작한다. 네트워크는 동기화·소셜로그인·**종목 자세 영상 재생**·(Phase 3)음식DB 갱신에만 사용한다. **종목 설명과 자세 가이드 이미지는 앱 내장 asset이므로 오프라인에서도 열람 가능**하다. | REQ-NFR-003, REQ-EXR-003 |
| P3 | **의존성 역전 (Clean Architecture)** | Domain 계층은 Android·Room·Retrofit 어디에도 의존하지 않는 순수 Kotlin. 바깥 계층이 안쪽을 향해서만 의존한다. | REQ-NFR-007 |
| P4 | **단방향 데이터 흐름 (UDF)** | UI는 상태를 렌더링만 하고, 이벤트를 위로 올린다. 상태는 ViewModel이 소유하고 `StateFlow` 하나로 노출한다. | REQ-NFR-007 |
| P5 | **즉시 영속 (No Save Button)** | 입력 이벤트는 디바운스 후 즉시 Room에 upsert. 명시적 저장 버튼에 의존하지 않는다. | REQ-WRK-011, FN-WRK-031 |
| P6 | **계산은 Domain에서** | 1RM·볼륨·강도·원판 계산은 전부 순수 함수 UseCase. UI/DB에 계산 로직을 두지 않는다(단위 테스트 80% 목표의 전제). | REQ-NFR-008 |
| P7 | **표시 시점 단위 변환** | 저장은 항상 SI(kg/cm/km). 변환은 Presentation 계층 경계에서만 수행한다. | REQ-CMN-003 |
| P8 | **확장 가능한 세트 스키마** | 종목 기록유형 5종에 따라 사용 컬럼이 달라지므로 `workout_set`은 유형별 컬럼을 nullable로 보유한다. | REQ-NFR-006, REQ-EXR-007 |

## 3. 앱 아키텍처 — Clean Architecture 3계층

### 3.1 계층 구조와 의존 방향

```
┌──────────────────────────────────────────────────────────────┐
│  Presentation Layer            (:app, :feature:*, :core:ui)   │
│  ─────────────────────────────────────────────────────────    │
│   Composable Screen  ──state──▶  렌더링                        │
│         │ event                                               │
│         ▼                                                     │
│   ViewModel  ── UiState(StateFlow) / UiEvent(Channel)         │
│         │                                                     │
└─────────┼─────────────────────────────────────────────────────┘
          │ 호출 (UseCase 인터페이스)
          ▼
┌──────────────────────────────────────────────────────────────┐
│  Domain Layer                  (:core:domain)  ★ 순수 Kotlin  │
│  ─────────────────────────────────────────────────────────    │
│   UseCase (비즈니스 규칙)                                      │
│   Model   (Exercise, WorkoutLog, WorkoutSet ...)              │
│   Repository **인터페이스**                                    │
│   Calculator (OneRepMax, Volume, Intensity, PlateSolver)      │
│                                                               │
│   ※ android.*, androidx.*, Room, Retrofit 의존 금지            │
└─────────▲─────────────────────────────────────────────────────┘
          │ 구현 (의존성 역전)
┌─────────┴─────────────────────────────────────────────────────┐
│  Data Layer      (:core:data, :core:database, :core:network)  │
│  ─────────────────────────────────────────────────────────    │
│   RepositoryImpl  ──▶ LocalDataSource  (Room DAO)   ★ SSoT    │
│                   ──▶ RemoteDataSource (Retrofit)   동기화 전용 │
│                   ──▶ PreferenceDataSource (DataStore)        │
│   Entity ↔ Model Mapper                                       │
└───────────────────────────────────────────────────────────────┘
```

**의존 규칙 (Gradle이 강제)**

| 계층 | 의존 가능 대상 |
|---|---|
| `:feature:*` | `:core:domain`, `:core:ui`, `:core:designsystem`, `:core:common` |
| `:core:data` | `:core:domain`, `:core:database`, `:core:network`, `:core:common` |
| `:core:database` / `:core:network` | `:core:common` |
| `:core:domain` | **없음** (순수 Kotlin 모듈, Android 플러그인 미적용) |

> `:feature:*` 는 `:core:data` 를 **직접 참조하지 않는다.** Repository 구현체 바인딩은 `:app` 의 Hilt 모듈에서만 수행한다.

### 3.2 계층별 데이터 표현

| 계층 | 타입 | 예시 | 변환 지점 |
|---|---|---|---|
| Presentation | UiState / UiModel | `SetRowUiModel(displayWeight="60.0 kg")` | ViewModel에서 단위·포맷 적용 |
| Domain | Model | `WorkoutSet(weightKg=60.0, reps=10)` | — (항상 SI 단위) |
| Data (Local) | Room Entity | `WorkoutSetEntity(weight_kg=60.0)` | Mapper |
| Data (Remote) | DTO | `WorkoutSetDto(weightKg=60.0)` | Mapper |

## 4. 핵심 시나리오별 데이터 흐름

### 4.1 세트 입력 (가장 빈번한 경로 — 100ms 이내 반영, REQ-NFR-001)

```
[사용자] 중량 입력 "60"
   │
   ▼
SetInputScreen ──onWeightChange(60.0)──▶ WorkoutViewModel
   │                                          │
   │  ① 낙관적 UI 갱신 (즉시)                   │
   │◀── uiState.copy(...) ───────────────────┘
   │                                          │
   │                                    ② debounce 300ms
   │                                          ▼
   │                                 UpsertWorkoutSetUseCase
   │                                          │
   │                                          ▼
   │                                 WorkoutRepositoryImpl
   │                                          │
   │                                          ▼
   │                                 WorkoutSetDao.upsert()  ★영속
   │                                          │
   │                                    ③ Flow 방출
   │◀─────────────────────────────────────────┘
   ▼
세션 요약(총 볼륨) 자동 재계산 → 표시
```

- **①** UI는 DB 왕복을 기다리지 않는다(낙관적 갱신).
- **②** 디바운스 300ms — 연타 입력 시 DB 쓰기 폭주 방지. (FN-WRK-031)
- **③** DAO가 `Flow<List<WorkoutSetEntity>>` 를 반환하므로 볼륨·강도 파생값은 자동 갱신된다.
- 앱이 강제 종료되어도 마지막 디바운스 확정분까지는 보존된다.

### 4.2 오프라인 → 온라인 동기화

```
[오프라인 기록]                     [네트워크 복구]
Room에 저장                    WorkManager (NetworkType.CONNECTED)
is_dirty = 1  ─────────────────▶ SyncWorker
                                       │
                     ┌─────────────────┴─────────────────┐
                     ▼                                   ▼
              ① PUSH (변경분 업로드)              ② PULL (서버 변경분)
       updated_at > lastSyncAt 인 레코드      GET /sync/pull?since=…
       + tombstone 목록 배치 전송                     │
                     │                                ▼
                     ▼                        서버 레코드와 로컬 비교
              서버: LWW 적용 후 확정본 반환       updated_at 늦은 쪽 채택
                     │                                │
                     └─────────────┬──────────────────┘
                                   ▼
                          Room upsert + is_dirty = 0
                          sync_state.last_synced_at 갱신
```

- 충돌 해소는 **Last-Write-Wins(updated_at 기준)** — REQ-DAT-002, FN-DAT-004
- 삭제는 물리 삭제 대신 `tombstone` 레코드 전파 — FN-WRK-004
- 상세 프로토콜은 [05_API설계서.md](./05_API설계서.md) §5 참조

### 4.3 휴식 타이머 (백그라운드 정확도)

```
세트 완료 체크 (FN-WRK-020)
   │
   ▼
RestTimerService (Foreground, type=health)
   │  startAt = SystemClock.elapsedRealtime()   ★ 시스템 시계 변경에 영향받지 않음
   │  targetMillis = 종목별 휴식시간 ?: 전역 기본값
   │
   ├─▶ Notification (진행형, 잔여시간 갱신)
   ├─▶ StateFlow<TimerState> ─▶ UI (수행 화면)
   └─▶ 종료 시 Vibrator + 알림음 + Notification
```

- 카운트다운은 `elapsedRealtime()` 델타로 산출한다. 코루틴 `delay` 누적은 백그라운드에서 드리프트가 발생하므로 표시 갱신에만 사용한다.
- Doze 모드에서도 Foreground Service는 유지된다. (REQ-TOL-001)

## 5. 저장소 전략

| 저장소 | 대상 데이터 | 선택 이유 |
|---|---|---|
| **Room (SQLite)** | 운동일지·세트·종목·루틴·체성분·식단 등 관계형 도메인 데이터 전부 | 관계·집계 쿼리 필요, 3년치 30,000세트 성능 요구(REQ-NFR-001) |
| **DataStore (Proto/Preferences)** | 온보딩 완료 여부, 마지막 선택 탭, 캘린더 필터 상태 등 **UI 로컬 상태** | 동기화 대상이 아닌 단말 로컬 값 |
| **`user_setting` 테이블** | 단위·테마·1RM 공식·기본 휴식시간 등 **동기화 대상 설정** | 기기 이전 시 승계되어야 함(REQ-DAT-004) |
| **앱 전용 내부 저장소**<br>`context.filesDir/photos/` | 눈바디 사진, 식단 사진 | MediaStore 미등록 → 갤러리 비노출(REQ-BDY-003, REQ-NFR-004) |
| **APK asset** `assets/guide/` | 종목 자세 가이드 이미지(WebP) | 읽기 전용·불변. 오프라인 열람 보장(REQ-EXR-003, FN-EXR-016) |
| **EncryptedSharedPreferences** | Access/Refresh Token | REQ-NFR-004 |
| **SAF (Storage Access Framework)** | 백업 JSON·CSV 내보내기 | 저장소 권한 불필요 |

> **설정 이원화 기준**: "새 기기에서도 그대로여야 하는가?" → 예이면 `user_setting` 테이블, 아니면 DataStore.

## 6. 성능 설계 (REQ-NFR-001)

| 요구 기준 | 설계 대응 |
|---|---|
| 운동일지 진입 **1초 이내** | ① 일지 헤더/종목/세트를 단일 `@Transaction` 관계 쿼리로 1회 조회 ② `LazyColumn` 지연 렌더링 ③ 파생 지표는 Flow로 후속 방출(초기 렌더 차단 안 함) |
| 세트 입력 반영 **100ms 이내** | 낙관적 UI 갱신 + DB 쓰기 비동기화(§4.1) |
| 종목 검색 **300ms 이내** | ① `exercise.name_chosung` 사전 계산 컬럼 + 인덱스 ② 검색어 debounce 200ms ③ `LIMIT 50` 페이징 |
| 3년치(30,000세트) 동일 성능 | ① 조회 축(`workout_log.workout_date`, `workout_set.log_exercise_id`)에 인덱스 ② 리포트 집계는 SQL `GROUP BY`로 DB에서 수행(앱 메모리 로딩 금지) ③ 차트는 기간 필터 후 조회 |
| 메모 통합 검색 | Room **FTS4** 가상 테이블 사용 (FN-RPT-019) |

## 7. 기술 스택 결정 근거

| 영역 | 선정 | 근거 / 대안 검토 |
|---|---|---|
| UI | **Jetpack Compose** | 세트 표·타이머 등 상태 변화가 잦은 화면에 선언형이 유리. XML View 대비 커스텀 컴포넌트 재사용 용이. |
| 아키텍처 | **Clean Architecture + MVVM(UDF)** | 계산 로직을 순수 함수로 격리해야 단위 테스트 80%(REQ-NFR-008) 달성 가능. |
| DI | **Hilt** | Compose·WorkManager·Service 통합 지원이 표준화되어 있음. Koin 대비 컴파일 타임 검증 우위. |
| 로컬 DB | **Room** | SQLite 위 타입 안전 계층 + Flow 반환 + FTS4 + Migration 지원. SQLDelight는 멀티플랫폼 이점이 있으나 iOS 미대상(Out of Scope)이라 불필요. |
| 비동기 | **Coroutines + Flow** | Room/WorkManager/Compose 전 구간 일관. |
| 통신 | **Retrofit + OkHttp + kotlinx.serialization** | 동기화 배치 전송에 인터셉터(토큰 갱신·로깅) 구성이 용이. |
| 백그라운드 | **WorkManager** | 네트워크 제약 조건 기반 지연 실행(REQ-NFR-003). 타이머는 성격이 달라 Foreground Service로 분리. |
| 차트 | **Vico** (또는 Compose Canvas 자체 구현) | Compose 네이티브 지원. MPAndroidChart는 View 기반이라 Interop 비용 발생. |
| 백엔드 | **Spring Boot 3 + Kotlin** | 앱과 언어 통일 → DTO·검증 규칙 재사용. JPA + Flyway로 스키마 이력 관리. |
| 서버 DB | **PostgreSQL 16** | 동기화 시 부분 인덱스·JSONB 활용 여지. 개인 서버 리소스 내 운영 가능. |
